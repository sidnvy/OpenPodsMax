# OpenPodsMax 0.2.3

**Prepared candidate — not yet published.** Version code: **6**.

This patch improves settings responsiveness and recovery of enabled Android playback features. It does not claim to resolve every intermittent wear-detection failure or make native Settings registration permanent.

## Changes

- Settings writes run off the UI thread. A stalled Bluetooth write times out instead of keeping the shared controller locked.
- Planned headset-settings readbacks reconnect after one second without accumulating the 1–30 second failure backoff. Genuine connection failures keep their backoff and audio-ownership checks.
- Keep recently confirmed settings visible during a bounded readback reconnect; values still require genuine headset confirmation.
- Recover the existing **Pause when removed** opt-in after app replacement, boot, Bluetooth return, or a connection from the approved headset. A transient service-start failure does not erase the opt-in.
- Add privacy-conscious wear diagnostics for event delivery, debounce and pause conditions. Logs do not intentionally record headset addresses, track titles or raw packets.
- Remove unverified button-cycle, Digital Crown direction, call and camera configuration surfaces. The working listening-mode selector remains.
- Mark Loud Sound Reduction as unavailable and distinguish headset sensor settings from Android pause/resume.

## Verified on Moto Edge 70 / Android 17

These observations used the same source fixes in an in-place, same-certificate test build before the 0.2.3 version bump:

- Four consecutive setting changes used one-second planned reconnects and independent device readback. The original Conversation Awareness value was restored.
- The user confirmed pause/resume after the setting roundtrips.
- After a deliberate background process crash, Android restored the sticky service, AAP connection and fresh worn baseline without opening the app.
- Build/lint and JVM regressions cover blocked writes, initialization packet boundaries, repeated planned readbacks, real failure backoff, session ownership and wear policies.

Version/signature/update checks on the final 0.2.3 APK and CI on its exact release commit remain separate release gates.

## Known limitations

- An earlier intermittent missed-pause occurrence remains unexplained. Short successful tests do not prove long-duration reliability.
- Actual reboot acceptance for this candidate remains pending. Boot recovery is implemented; process-reclaim recovery is the hardware case already verified.
- Native Android device artwork and enhanced device pages need experimental device-specific registration. Google or the system can overwrite it during Bluetooth cycles or updates; the ordinary APK cannot restore privileged metadata automatically.
- Simultaneous multipoint and automatic switching between hosts are not implemented. Another previously paired host can take the headset on wake.
- The current conservative pause policy requires both cups to report removal. A one-cup transition is ignored. Resume also requires a safe, current session and the same player that this app paused.
- Android 17 may silently mute resumed background playback depending on the player and controller lifecycle and their while-in-use audio capabilities. In the Moto test, YouTube Music playback was active on A2DP but muted by `opControlAudio`; opening the player restored sound. A successful play request does not guarantee audible output. This release does not bypass Android audio-hardening restrictions. See [Android's background-audio guidance](https://developer.android.com/about/versions/17/changes/bg-audio).
- Unsupported or unreported headset controls remain unavailable. Adaptive Audio strength persistence is not verified.

## Update

Official 0.2.x installations can update in place with the same release certificate. Do not uninstall or clear app data for an ordinary same-key update. Debug/private builds signed with another certificate cannot be updated directly by an official APK; see [release verification](../RELEASING.md).
